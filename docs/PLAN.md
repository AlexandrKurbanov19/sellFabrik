# План реализации: фабрика SEO-лендов для партнёрки Leads Market

**Статус:** черновик v0.1 (требует подтверждения открытых вопросов из §13)
**Дата:** формируется по документу `pulse.xlsx` и открытым данным Leads Market
**Стек (заявлен):** Next.js + Strapi CMS + PostgreSQL, один домен, программатик-SEO

---

## 0. TL;DR

Строим **программатик-SEO платформу** на одном домене: `направление × город` → ленд с формой
(уходит лидом в партнёрку) или телефоном (звонок в колл-центр по нашему ID).

Ключевые архитектурные принципы:

1. **Партнёрка — сменный адаптер.** Всё взаимодействие с CPA-сетью инкапсулировано в
   `LeadProvider`. Сейчас — Leads Market, в будущем — любой другой без переписывания лендов.
2. **Доступность `направление × город` — данные, а не контент.** Еженедельный `pulse.xlsx`
   (или API `/api/partners/pulse`) синхронизируется в БД. Ленд публикуется/снимается автоматически.
3. **Один домен, одна структура URL**, города и направления — вложенные сегменты.
4. **Уникальность контента обязательна** — иначе Яндекс зарежет как «малополезный/дорвейный» контент.
5. **Приоритезация по Wordstat** — какие пары строить первыми, решает спрос × выплата × доступность.

## 2. Как работает партнёрка (модель Leads Market)

### 2.1 Экономика
- CPA: оплата за **выполненную заявку** (не за клик).
- Два тарифа: **фикс (до 1200 ₽)** и **процент (до 26%)** от чека.
- Выплаты еженедельно, статистика в реальном времени, есть холд/апрув.

### 2.2 Каналы передачи лида
1. **Форма на ленде → API партнёрки.** Кабинет выдаёт `leads_url` (URL с вшитым токеном), куда
   POST-запросом уходит заявка. Возможен отдельный read-ключ для статистики/выгрузки.
2. **Телефон → колл-центр партнёрки** по нашему партнёрскому ID (звонок атрибутируется нам).
3. **Обратный вебхук** (`webhook_url`) — партнёрка пушит к нам статусы заявок (апрув/отклонение/выполнено).
   Это нужно для сквозной аналитики (какой ленд/UTM дал деньги, а не просто лид).

### 2.3 Что важно из интерфейса кабинета
- Раздельные ключи: «Отдельный ключ для статистики и заявок», «Перевыпустить ключ чтения».
- Журнал запросов интеграции, лог изменений, тестовая заявка.
- Токен в ссылке — его нельзя публиковать (передавать форму нужно через наш серверный прокси).
- `/api/partners/pulse` — серверный аналог `pulse.xlsx` (статусы × гео), можно не парсить XLSX вручную.

### 2.4 Альтернативные партнёрки
Изучены альтернативы, чтобы **не зависеть от одного провайдера**. Полный разбор — в
[`research/alternatives.md`](research/alternatives.md). ServiceLead исключён (невыплаты,
см. [`research/affiliates.md`](research/affiliates.md)).

Кандидаты в **резервные адаптеры**:
- **Руки из плеч** (`cpa.ruki-iz-plech.ru`) — прямой рекламодатель, широкое покрытие наших
  направлений (окна, сантехника, электрика, дезинсекция, техника), автоматизация, еженедельные выплаты.
- **FirstLead** (`firstlead.ru`) — широкий список услуг, **выдаёт телефонные номера**, еженедельные выплаты.
- Доп.: FIXCPA (600–1500 ₽, только МСК/СПб/ЕКБ), ASC-Service (выкуп лидов, 30+ городов).

> **РЕШЕНИЕ:** Leads Market — **основная** партнёрка для MVP. При этом `LeadProvider` (§6)
> проектируется сразу как **мульти-адаптер**: второй провайдер (Руки из плеч / FirstLead)
> подключается без переписывания лендов. Роутинг `направление × город → провайдер` включаем,
> когда основной не покрывает пару или недоступен.

### 3.3 Семантика статусов — ⚠️ ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ
Наблюдаемые значения «Актуальный Статус»: `Увеличить`, `Отключить`, `без изменений`.
Наблюдаемые переходы (`Статус до изменения` → `Актуальный Статус`) включают
`без изменений → Увеличить`, `Увеличить → без изменений`, `Увеличить → Отключить`.

Пока принимаем (гипотеза, вынести в конфиг):
- `Увеличить` — направление доступно, льём трафик/принимаем лиды 🟢
- `Отключить` — недоступно, ленд снимаем 🔴
- `без изменений` — **нужно уточнить**: «оставить как было» (тогда нужен внешний источник
  текущего состояния) либо «нейтрально/доступно». От этого зависит счёт страниц (375 vs 527).

### 3.4 Стоп-факторы
Лист «СТОП-ФАКТОРЫ» содержит:
- блоки «Выполняем работы / НЕ выполняем работы» по каждому направлению (что чиним, что не чиним);
- ограничения по возрасту/типу техники, брендам, типам объектов (промышленное, газовое и т.п.).

**Вывод:** стоп-факторы надо использовать **двумя способами**:
1. контент — честный блок «Что мы не делаем» (повышает доверие и качество трафика);
2. **валидация лида на нашей стороне** — не отправлять в партнёрку заведомо отклоняемые заявки,
   чтобы не портить апрув и не жечь трафик.

## 4. Архитектура решения

```
                    ┌───────────────────────────────────────────────┐
   pulse.xlsx ─────▶│  Strapi (headless CMS)                        │
   /api/partners/   │  · Direction/City/Availability/Landing        │
   pulse            │  · Affiliate + секреты                        │
   (weekly sync)    │  · Keyword/Wordstat                           │
                    │  · Lead log                                   │
                    └───────────────┬───────────────────────────────┘
                                    │ REST/GraphQL + webhook publish
                                    ▼
   Пользователь ──▶ ┌───────────────────────────────┐   server-side POST    ┌──────────────┐
                    │  Next.js (App Router, ISR)    │──────────────────────▶│ Leads Market │
                    │  · ленды {direction}/{city}   │   (leads_url+token)   │  (leads_url) │
                    │  · хабы, sitemap, schema.org  │                       └──────┬───────┘
                    │  · /api/lead (proxy)          │◀──── webhook статусов ────────┘
                    └───────────────┬───────────────┘
                                    │ цели Метрики / GA4 / UTM
                                    ▼
                             Аналитика и сквозной ROI
```

### 4.1 Компоненты
| Компонент | Роль | Технология |
|---|---|---|
| `web` | Публичный сайт, программатик-SEO, формы, прокси лидов | Next.js (App Router), ISR + on-demand revalidation |
| `cms` | Источник данных, редактура контента, матрица доступности | Strapi v5 + PostgreSQL |
| `sync` | Парсинг `pulse.xlsx`/API, upsert доступности, diff, ревалидация | Node worker / cron (Strapi cron или отдельный процесс) |
| `wordstat` | Сбор частотностей, скоринг приоритетов | Node worker + Yandex Search API (или сторонний парсер) |
| `db` | Данные | PostgreSQL |
| `cache/queue` | Очереди ревалидации, ретраи вебхуков (опц.) | Redis / BullMQ |

### 4.2 Почему так
- **Strapi как единый источник истины** для направлений, городов, контента и доступности.
- **Next.js ISR**: сотни страниц рендерятся статически (быстро, дёшево, хорошо для SEO), но обновляются
  по требованию при изменении в CMS/при синке `pulse`.
- **Серверный прокси `/api/lead`**: токен партнёрки не светится в браузере, работает валидация
  стоп-факторов, логирование, дедупликация и сквозные UTM.

## 6. Слой партнёрок: `LeadProvider` (сменные адаптеры)

```ts
interface LeadProvider {
  code: string;
  canHandle(direction: Direction, city: City): Promise<boolean>;
  submitLead(input: LeadInput): Promise<SubmitResult>;      // форма → leads_url
  getPhoneTarget(direction, city): Promise<PhoneTarget>;     // call-ленды
  parseStatusWebhook(req: Request): Promise<StatusEvent>;    // апрув/отказ
  getAvailability(): Promise<AvailabilityRow[]>;             // pulse API, если есть
}
```

- **`LeadsMarketAdapter`** (MVP, основной):
  - `submitLead` → серверный POST на `leads_url` с токеном, маппинг полей + UTM.
  - `parseStatusWebhook` → приём `webhook_url` со статусами, обновление `lead.status`.
  - `getAvailability` → `GET /api/partners/pulse` (если токен) либо парсинг `pulse.xlsx`.
- **Роутинг (на будущее):** при нескольких партнёрках — правило `(direction, city) → affiliate`
  с `priority`, весом и A/B. **В MVP не реализуется** — провайдер один (Leads Market); в модели
  достаточно одного поля `affiliate` в `availability`/`landing`.
- **Секреты:** только через env / приватные поля Strapi; ротация токенов не трогает код.
- **Failover (один провайдер):** при ошибке отправки — ретрай с backoff и уведомление; при недоступности оффера — страница уходит в 410/заглушку (см. §7.1).

> Смена партнёрки = новый адаптер + строка в `affiliate`. Ленды, URL, контент не меняются.
> Кандидаты и риск-профили — в `research/alternatives.md` и `research/affiliates.md`.

## 7. Доступность `направление × город` и блокировки

### 7.1 Правило публикации
Ленд `/{direction}/{city}` доступен (200) **если**:
`availability(direction, city).status == active` **и** существует партнёрка, которая `canHandle`.

Иначе (по политике, настраиваемо):
- `410 Gone` — если направление снято (сохраняем корректный сигнал для поисковика), **или**
- `301` на хаб города `/{city}`, **или**
- страница-заглушка с альтернативными направлениями.

Политику выбираем осознанно: 410/301 — чтобы не копить мусорный индекс.

### 7.2 Синхронизация `pulse`
Процесс (еженедельно, напр. понедельник):
1. Источник: `pulse.xlsx` (загрузка в Strapi) или `/api/partners/pulse`.
2. Нормализация города: матч по `name` + `aliases` + `parentDepartment`. **Отдельный шаг — fuzzy-матч и ручная очередь на разбор** (имена спутников и опечатки).
3. Upsert `offer-availability`, запись `rawStatus` и истории.
4. Diff → список включённых/выключенных пар.
5. Автообновление `landing.status`.
6. On-demand revalidation затронутых страниц.
7. Уведомление в Telegram + лог.
8. Обновление `sitemap`.

### 7.3 Стоп-факторы как правила
- Хранить как структурированные правила (JSON) на уровне направления + оверрайды на город.
- Применять в:
  1. **контенте** — блок «Не выполняем»;
  2. **валидации лида** — отбрасывать заведомо непроходные заявки до отправки в партнёрку.

## 8. Ленды: форма, телефон, коллтрекинг

### 8.1 Режим «Форма»
- Клиент заполняет форму → `/api/lead` (наш сервер) → валидация → `LeadProvider.submitLead`.
- Скрываем токен, пишем `lead` в БД, ставим цель Метрики, прокидываем UTM/click-id.
- Ответ клиенту не раскрывает партнёрку.

### 8.2 Режим «Телефон / колл-центр»
- На странице — номер, привязанный к паре `(partnerId, direction, city)`.
- Варианты:
  - **Статический номер на странице** — идеален для SEO (номер в HTML), но хуже для атрибуции;
  - **Динамическая подмена (DNI)** через провайдера коллтрекинга — точная атрибуция, но номер
    приходит JS-ом (для SEO хуже; можно комбинировать: статический «запасной» + DNI).
- Нужно решить: используем **номера Leads Market** или свой коллтрекинг (Mango/Calltouch/Telfin/Sipuni)
  с маршрутизацией на их ID.

### 8.3 Гибрид (рекомендуется)
Статический номер + форма, оба канала ведут к одному партнёру; цель — и звонок, и заявка.

## 9. SEO-стратегия

### 9.1 URL-структура (один домен)
```
/                                  — корень (выбор города/услуги)
/{direction}                       — хаб направления (список городов)
/{city}                            — хаб города (список направлений)
/{direction}/{city}                — ЛЕНД (основная единица)
/{direction}/{city}/{brand}        — фаза 2 (бренд × услуга)
```
- Только один уровень вложенности на ленд, ЧПУ, `lowercase-kebab`.
- Единая политика слэша, канонические URL, 301-карта при изменениях slug.

### 9.2 Уникальность контента (главный риск)
Шаблон «подставили город» = дорвей → фильтр Яндекса. Митигации:
- **Уникальные блоки на каждый ленд:** локальные районы/ориентиры, особенности, реальные отзывы,
  цены, сроки, мастера.
- **Порог качества**: минимум уникального текста, проверка на дубли (внутренний дифф + сервисы).
- **Публикация волнами** (не 500 страниц за раз), мониторинг индексации в Яндекс.Вебмастере и GSC.
- **Контент-пайплайн**: LLM-черновик + редактор + факт-чек; фиксировать `qualityScore` и `lastReviewedAt`.

### 9.3 Коммерческие факторы Яндекса
Для коммерческих запросов важны: реальные контакты, юр. информация, цены, оферта, политика
конфиденциальности, отзывы, скорость, мобильная версия. Заложить в шаблон.

### 9.4 Технический SEO
- `sitemap.xml` (индекс + сегментированные: направления, города, ленды, бренды), `robots.txt`.
- Schema.org: `LocalBusiness`, `Service`, `Offer` (цена), `FAQPage`, `BreadcrumbList`, `AggregateRating`.
- OpenGraph/Twitter, favicon, `lang="ru"`.
- Core Web Vitals: статика/ISR, оптимизация изображений, отсутствие блокирующего JS.
- Внутренняя перелинковка: соседние города региона, другие направления города, хлебные крошки.
- `410/301` для снятых пар (см. §7.1).
- Яндекс.Вебмастер: подтверждение, регион, турбо-страницы (опц.), мониторинг.

### 9.5 Аналитика
- Яндекс.Метрика + GA4, цели: отправка формы, клик по телефону, звонок.
- Сквозной UTM до `lead`, привязка статусов из `webhook_url` → **ROI по ленду**, а не только «лиды».
- Дашборд: трафик → лиды → апрув → выплата по `направление × город`.

## 10. Wordstat-модуль (приоритезация)

### 10.1 Источники
- **Официально:** Yandex Search API → Wordstat (Yandex Cloud, платно, синхронно).
- **Альтернативы:** XMLRiver / arsenkin / pixelplus (сторонние API парсинга).

### 10.2 Матрица запросов
Генерация паттернов на `direction × city`:
`«{услуга} {город}»`, `«ремонт {техника} {город} цена»`, `«вызвать мастера {город}»`,
`«{услуга} на дому {город}»`, `«{бренд} ремонт {город}»`.
Регион = город/область; сохраняем базовую и точную частотность, сезонность по месяцам.

### 10.3 Скоринг приоритета
```
DemandScore = w1·Wordstat(city) + w2·Payout + w3·IsActive + w4·(1 − Competition)
```
Ранжируем пары → строим ленды сверху вниз. Сезонность → календарь публикаций и контент-плана.

### 10.4 Артефакты
- Таблица `keyword` / `keyword-stat` в Strapi.
- Экспорт `docs/analytics/wordstat-priority.csv` (после подключения API).
- Регулярность: раз в месяц + в начале сезонов.

## 12. Риски и митигации

| Риск | Влияние | Митигация |
|---|---|---|
| Фильтр Яндекса за дорвей/малополезный контент | Потеря трафика | Уникальный контент, порог качества, волны, мониторинг |
| Зависимость от одной партнёрки (Leads Market) | Обрыв денег | Адаптер `LeadProvider` как задел под смену; мониторинг выплат; резервный провайдер — при необходимости |
| Низкий апрув из-за непроходных заявок | Потеря денег и репутации | Валидация по стоп-факторам, честные «мы не делаем» |
| Ошибки матчинга городов (спутники/алиасы) | Лиды не туда, отказы | Alias-таблица, ручная очередь разбора, тесты синка |
| Токен партнёрки утёк в браузер | Злоупотребление | Только серверный прокси `/api/lead` |
| Персональные данные (152-ФЗ) | Юр. риск | Согласие, политика, шифрование, DPA с партнёркой |
| Коллтрекинг ломает SEO | Просадка | Комбинация статический номер + DNI |
| Блокировка направлений меняется еженедельно | Битые ленды | Авто-снятие/301/410 + уведомления |
| Рост цен на Wordstat API | Затраты | Кэш, выборочный сбор, сторонний парсер |
